## Architecture and responsibility map

| Module | Responsibility |
| --- | --- |
| `acc/core.py` | Persistent tasks/events, one writer, supervised subprocesses, deadlines, recovery, local Git observation |
| `acc/workflow.py` | Sequential implementation → coordination → independent review → coordination; bounded correction rounds |
| `acc/controls.py` | Persistent switches after the current step, priorities and dependency-cycle checks |
| `acc/conversation.py` | Exact messages, routing, external leases, transactional reply/task acknowledgement, fallback |
| `acc/voice.py`, `acc/transcribe.py` | Saved recordings, supervised transcription, optional local faster-whisper adapter |
| `acc/snapshots.py` | Frozen review copies, file hashes and drift verification |
| `acc/github.py` | Dated remote activity cache, reviewed publication preview, commit/push/PR reconciliation |
| `acc/server.py`, `acc/web/` | Authenticated loopback HTTP, event stream, conversation/dashboard controls |
| `acc/bridge.py` | MCP stdio client-facing tools forwarding to ACC HTTP |
| `acc/hermes.py` | Hermes one-shot CLI adapter and MCP configuration generation |
| `acc/setup.py`, launchers | Persistent host configuration, diagnostics and launch |

The **LLM is the planner/decision-maker; the Python coordinator is the persistent executor and state machine**. Hermes is an agent host with tools and configured models, not a magic replacement for process supervision. MCP exposes operations/context; it is not by itself an agent heartbeat or proof that every desktop/mobile chat is connected.

ACC does not inspect unrelated ChatGPT conversations. A connected orchestrator explicitly reads/sends/claims/completes through the bridge. A phone conversation reaching a desktop application does not automatically register ACC's MCP tools. The actual desktop host connection remains a laptop check.

## Implemented behavior and its boundaries

### Conversations, remote ownership and offline use

- Exact text is saved with stable IDs; identical retries deduplicate. Browser IndexedDB retains an outbox, including recordings, for reconnection.
- External MCP orchestration uses read/send/claim/renew/complete/release/retry. External leases last 120 seconds; renew while reasoning. Completion atomically saves the reply, validated task actions and message acknowledgement.
- A supervised configured planner handles local turns. A permitted local planner can follow failed preferred-planner attempts after the prior process ends and project integrity is checked. New turns try the preferred online adapter again.
- Workflow offline mode selects permitted local roles. Automatic coordinator fallback is supported where safe. Arbitrary partially edited failed implementation runs are held for inspection; there is no universal immediate online/offline takeover.
- Offline capability requires local model weights, runtime, code, tools and dependencies to be installed already. Executable detection and `local:true` are not proof of actual offline inference.
- Audio is saved before transcription. The optional adapter uses a predownloaded faster-whisper model with CPU/int8 defaults. No per-minute cloud transcription request is made by that adapter. Package/model availability and microphone quality are host checks.

### Assignment and scheduling

- Preferred workflow roles, active agent and run history are distinct.
- **Switch after current step** records the request immediately. The running step finishes; the selected role changes afterward, retaining files and history. It does not resume the previous model's private reasoning or force-stop it mid-step.
- Replacing a reviewer invalidates the old verdict and requires fresh review. The actual implementer adapter cannot independently approve its own snapshot.
- **Stop now** interrupts supervised work; retained partial changes require inspection before continuing.
- Identical switch-request replay is handled, including after task acceptance. Restart recovery cancels pending switches and requires explicit assignment after process inspection.
- Higher numeric task priority runs first. All named prerequisites must be accepted. Cycles are rejected. One writer per shared workspace remains enforced.
- POSIX process groups are supervised. Windows uses taskkill; job-object/detached-child containment remains unverified. Adapters must stay attached and not daemonize.

### Reviews and publication

Exit code zero is completion, not approval. Managed results are bound to task ID, run ID, requirement revision and snapshot ID. Snapshot or project drift blocks acceptance/publication. The manual reported-review route is weaker than managed review and cannot bypass managed acceptance.

Local output streams directly. Local Git is reconciled about once a second. GitHub uses outbound CLI/API polling, default 30 seconds and configurable 15–300 seconds, plus manual refresh. There is no GitHub webhook receiver. Remote results retain a last-success timestamp and stale status when unavailable; do not promise instantaneous outside GitHub activity.

Publication is explicit: inspect accepted task → preview → publish. It captures the initial task baseline, rejects unrelated dirty/staged work and overlapping prior edits, verifies the reviewed snapshot, creates a local commit when needed, performs a non-force push, and creates or reuses the source/base PR. It verifies the remote commit and PR head. No automatic merge or branch deletion is implemented.

Preview binds expected committed content, source/base/remote refs and outgoing/full PR commit lists. Git built-in line-ending conversions and `core.filemode=false` are supported; hook-altered content/modes are rejected. A new reviewed cycle at the same requirement revision is distinguished by snapshot ID. Failed/uncertain operations retain state for inspection and reconciliation. Publication reserves the project against workers and external conversation claims; uncertain process cleanup retains recovery ownership.

**Current asset boundary:** snapshots are limited to 10,000 files / 100 MiB and reject unsupported file types. Arbitrary Git clean filters, including LFS, require manual publication. Do not point whole-asset Hearth & Havoc at automatic publication and assume it has been validated. Plan scoped code reviews/asset receipts before expanding this path.
